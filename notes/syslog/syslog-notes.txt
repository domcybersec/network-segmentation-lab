SYSLOG / CENTRALIZED LOGGING NOTES
==================================

Purpose
-------
Syslog provides centralized event logging for network devices.

Instead of checking the console or local log buffer on every router and
switch individually, devices can forward operational and security-related
messages to a centralized Syslog server.

This is useful for:

- Troubleshooting
- Monitoring device status
- Detecting configuration changes
- Tracking interface state changes
- Security monitoring
- Incident investigation
- Correlating events between multiple devices

In this lab, the Infra-Server in VLAN 50 acts as the centralized Syslog
server for the network.

BASIC CISCO SYSLOG CONFIGURATION
--------------------------------

The following command was configured on each router and switch:

Example:

conf t

end


SYSLOG VERIFICATION
-------------------

The primary IOS verification command used was:

show logging

Example output included:

Trap logging: level informational

Logging to 192.168.50.10 (udp port 514, audit disabled,
 authentication disabled, encryption disabled, link up)

This confirms that the device has a remote logging destination configured
and is forwarding Syslog messages to 192.168.50.10 using UDP port 514.


SYSLOG SEVERITY LEVELS
----------------------

Cisco Syslog messages use severity levels from 0 through 7.

0 - Emergency
    System is unusable.

1 - Alert
    Immediate action is required.

2 - Critical
    Critical condition.

3 - Error
    Error condition.

4 - Warning
    Warning condition.

5 - Notification
    Normal but significant condition.

6 - Informational
    Informational message.

7 - Debugging
    Debug-level information.

IMPORTANT:

A LOWER Syslog number represents a MORE severe event.

For example:

Severity 2 = more severe than Severity 6.


TRAP LOGGING LEVEL
------------------

Packet Tracer did not support the expected commands:

logging trap informational

or:

logging trap 6

The available Packet Tracer CLI options were limited.

However:

show logging

confirmed:

Trap logging: level informational

Therefore, the devices were already forwarding messages through severity
level 6 (Informational).

This is a Packet Tracer CLI limitation rather than a requirement to change
the design.

SW4 MANAGEMENT CONFIGURATION
----------------------------

While integrating SW4 with centralized network services, SW4 initially had
no management IP address.

The branch network uses:

192.168.40.0/24

A dedicated local branch VLAN was created:

VLAN 40
Name: Branch

SW4 ports:

Fa0/1 -> R2
Fa0/2 -> Branch-PC

Both were assigned to VLAN 40.

Configuration:

vlan 40
 name Branch

interface fa0/1
 description R2-BRANCH-GATEWAY
 switchport mode access
 switchport access vlan 40

interface fa0/2
 description BRANCH-PC
 switchport mode access
 switchport access vlan 40

SW4 received the management address:

192.168.40.2/24

Configuration:

interface vlan 40
 description BRANCH-MANAGEMENT
 ip address 192.168.40.2 255.255.255.0
 no shutdown

ip default-gateway 192.168.40.1

Verification showed:

Vlan40    192.168.40.2    up    up

This allows SW4 to be remotely managed through the routed branch network.

HQ VLAN 99 was NOT extended across the WAN.

Instead, the branch switch uses its local VLAN 40 SVI for management.

SW4 could also reach R2's WAN interface:

SW4 -> 203.0.113.3 = SUCCESS

However, SW4 could not initially reach:

The Branch-PC also failed to reach 192.168.50.10.

This proved that the problem was not specific to the SW4 management SVI.


ROUTING VERIFICATION
--------------------

R2 correctly learned VLAN 50 through OSPF:

192.168.50.0/24
via 203.0.113.2

R2 itself could successfully ping:

192.168.50.10

R1 also correctly learned the Branch LAN through OSPF:

192.168.40.0/24
via 203.0.113.3

Therefore, bidirectional OSPF routing was working correctly.


NAT TROUBLESHOOTING
-------------------

R2 was originally configured to PAT all traffic sourced from:

192.168.40.0/24

using:

access-list 1 permit 192.168.40.0 0.0.0.255

ip nat inside source list 1 interface GigabitEthernet0/0/0 overload

This caused traffic from the Branch LAN to HQ internal networks to be
translated unnecessarily.

A Branch-PC ping to 192.168.50.10 created translations similar to:

Inside local:
192.168.40.10

Inside global:
203.0.113.3

Outside:
192.168.50.10

Therefore, R2 was performing PAT on Branch-to-HQ traffic.


NAT EXEMPTION SOLUTION
----------------------

The simple standard NAT ACL was replaced with an extended ACL that
distinguishes internal HQ traffic from Internet-bound traffic.

Configuration:

ip access-list extended BRANCH-NAT
 deny ip 192.168.40.0 0.0.0.255 192.168.10.0 0.0.0.255
 deny ip 192.168.40.0 0.0.0.255 192.168.20.0 0.0.0.255
 deny ip 192.168.40.0 0.0.0.255 192.168.30.0 0.0.0.255
 deny ip 192.168.40.0 0.0.0.255 192.168.50.0 0.0.0.255
 deny ip 192.168.40.0 0.0.0.255 192.168.99.0 0.0.0.255
 permit ip 192.168.40.0 0.0.0.255 any

PAT was then configured using:

ip nat inside source list BRANCH-NAT interface GigabitEthernet0/0/0 overload

IMPORTANT:

The deny statements in BRANCH-NAT do NOT deny the actual network traffic.

Because this ACL is being referenced by NAT, the deny statements mean:

"Do not translate this traffic."

The permit statement means:

"Translate matching traffic."

Final behavior:

Branch -> VLAN 10     No NAT
Branch -> VLAN 20     No NAT
Branch -> VLAN 30     No NAT
Branch -> VLAN 50     No NAT
Branch -> VLAN 99     No NAT
Branch -> Other       PAT

After the change:

Branch-PC -> 192.168.50.10 = SUCCESS

Branch-PC -> 198.51.100.10 = SUCCESS

Therefore:

Branch-to-HQ traffic remains routed normally through OSPF.

Branch-to-Internet traffic continues to use PAT.

NTP AND SYSLOG RELATIONSHIP
---------------------------

NTP and Syslog are separate services, but they are commonly deployed
together.

NTP provides consistent device time.

Syslog records events.

Accurate synchronized timestamps make it much easier to correlate events
between routers, switches, servers, firewalls, and security tools.

For example:

14:03:10 - SW1 interface goes down
14:03:12 - R1 routing event occurs
14:03:15 - Monitoring system reports connectivity loss

Without synchronized clocks, determining the true order of events becomes
much more difficult.


PACKET TRACER LIMITATIONS
-------------------------

Several Packet Tracer limitations were observed.

1. Syslog Time Column

The Packet Tracer Syslog server displayed "-" in the Time column instead
of rendering useful timestamps.

2. HostName Column

Packet Tracer displayed source IP addresses rather than useful configured
hostnames.

3. Message Display

The Syslog table visually truncated messages.

Selecting/highlighting an individual row displayed the complete message.

4. Syslog Trap CLI

Packet Tracer did not fully support normal IOS commands such as:

logging trap informational

However, show logging confirmed that the default trap level was already
Informational.

5. NTP Behavior

Packet Tracer produced stale/phantom NTP associations on branch devices,
including an unexpected association with:

203.0.113.2

even when the intended configured NTP server was:

192.168.50.10

SW4 also initially had a clock date in 1993. The clock was manually moved
near the server's 2026 time before allowing NTP to continue.

The intended NTP architecture remains:

Network Devices
      |
      v
192.168.50.10
Infra-Server

These NTP behaviors were treated as Packet Tracer simulation limitations
rather than redesigning a correctly routed network around simulator
behavior.

KEY LESSONS
-----------

1. Syslog centralizes operational and security events from multiple
   infrastructure devices.

2. Cisco Syslog severity levels range from 0 through 7, with lower
   numbers representing greater severity.

3. Cisco devices commonly send Syslog traffic using UDP port 514.

4. show logging can verify the configured logging server, trap level,
   and message activity.

5. Generating a controlled interface-state change is a simple way to
   verify end-to-end Syslog functionality.

6. Centralized logging is significantly more useful when devices also
   have synchronized clocks.

7. A Layer-2 switch requires a management SVI and default gateway to
   communicate with devices outside its local subnet.

8. A branch does not need to extend an HQ management VLAN across the WAN
   simply to provide switch management.

9. NAT ACLs define which traffic is translated. They should distinguish
   internal routed traffic from Internet-bound traffic when necessary.

10. A deny statement in an ACL used for NAT exemption means "do not
    translate," not necessarily "drop the packet."

11. Troubleshooting should isolate each layer before changing
    configurations:

    - Verify local connectivity
    - Verify default gateway
    - Verify routing
    - Verify return routing
    - Inspect NAT
    - Inspect ACLs
    - Verify the application/service

12. Packet Tracer can simulate centralized Syslog effectively, but its
    Syslog and NTP implementations have GUI and protocol limitations.
